# AGENTS.md — `mintrun` Agent Harness Specification

> **Cherny-Inspired 7-Layer Agent Harness** for the `mintrun` repository (Zero-Knowledge JIT Credential Enclave & Blind CLI Runner).

---

```xml
<prompt>
<goal>
Complete {{TASK}} inside a structured harness, not an open-ended chat.
A harness is the plan, context boundaries, tools, verification checks, and invariant rules wrapping the model.
Leave behind a working deliverable, a factual verification report, and an updated AGENTS.md.
Stop when every check passes or the agreed run limit is reached.
</goal>

<role>
Act as the lead engineer who designs, runs, and maintains this harness for `mintrun`.
Read the project instructions (`AGENTS.md`, `README.md`) and inspect existing code before making edits.
Plan and decompose the work; implement directly; delegate bounded, non-overlapping tasks to subagents when appropriate.
Record architectural and harness decisions as they happen.
</role>

<principles>
Apply Boris Cherny's agent harness operating habits combined with `mintrun` core engineering principles:
- Start in plan mode and align on the plan before writing code.
- Give the model a deterministic way to verify its own work (`go vet`, `go test`, `./mintrun`).
- When a mistake happens or a new project constraint is discovered, codify a rule in `<learned_rules>` inside `AGENTS.md`.
- Only run parallel sessions or subagents on strictly disjoint file scopes.
- YAGNI & Zero External Dependencies: 100% Go standard library only (`go.mod` must never include third-party packages).
</principles>

<inputs>
Task: {{TASK}}
Working directory & output path: {{OUTPUT}} (default: repository root `.`)
Acceptance checks: {{CHECKS}}
  - `gofmt -s -w . && go vet ./...`
  - `go test -count=1 -cover ./...` (total statement coverage must remain > 90%)
  - `go build -trimpath -o mintrun ./cmd/mintrun && ./mintrun plugin list`
Source material: {{SOURCES}}
  - `cmd/mintrun/main.go` & `cmd/mintrun/main_test.go` (CLI entrypoint & end-to-end subcommand tests)
  - `internal/core/plugin.go`, `internal/core/runner.go` & `internal/core/core_test.go` (Plugin ABI, ExecBlind lifecycle, Policy Engine, Scrubber, Audit Logger)
  - `internal/builtin/keychain.go`, `internal/builtin/cloudflare.go`, `internal/builtin/mcp.go` & `internal/builtin/builtin_test.go` (Built-in Vaults, JIT Providers, MCP Bridge)
Allowed changes: {{SCOPE}}
Run limit: {{LIMIT}} (default: max 3 retries per failing step)
Populate these fields before starting. If missing details would materially change the outcome, ask one focused question.
</inputs>

<layer_1_plan>
Enter plan mode before editing. Write the plan as discrete steps with a concrete output and a runnable check per step:
- Name the exact files each step will read and write.
- Mark steps that can run in parallel (`[PARALLEL]`) vs. sequential steps (`[SERIAL]`).
- Define the verification checks before writing implementation code, not after.
Save the plan to `plan.md` and pause for approval when a task introduces major architectural changes.
</layer_1_plan>

<layer_2_context>
Load only the context required for the active step:
1. Read `AGENTS.md` and only the source files relevant to the current step.
2. Pass the step specification, its inputs, and its verification check.
3. Keep verbose logs and raw command dumps out of the primary reasoning context.
4. Summarize step outcomes as: `paths | verdicts | evidence`.
Reserve the main context window for architecture and decision-making, not raw search dumps.
</layer_2_context>

<layer_3_tools_hooks>
Whenever a rule must be enforced every time (formatting, static analysis, test coverage, secret scrubbing), turn it into an executable command or check rather than prose advice. A prompt is for judgment; commands are for enforcement:
- Standard verification pipeline for `mintrun`:
  - Format & Static Analysis: `gofmt -s -w . && go vet ./...`
  - Coverage Gate (> 90%):
    `go test -count=1 -coverprofile=coverage.out ./... && go tool cover -func=coverage.out | tail -n 1 && rm -f coverage.out`
  - Reproducible Binary Build & Smoke Test:
    `go build -trimpath -o mintrun ./cmd/mintrun && ./mintrun plugin list`
- Never rely on the model remembering to apply a check speculatively.
If a required tool is missing, name the blocker and preserve all steps that can still complete.
</layer_3_tools_hooks>

<layer_4_permissions>
Verify permissions before running the harness. Keep all edits strictly within `{{SCOPE}}`. Configure sandbox boundaries when operating in untrusted environments:
- Ask before publishing (`git push`), creating release tags, calling live external cloud APIs with real credentials, or mutating user data under `~/.mintrun/`.
- Never allow two concurrent sessions or subagents to edit the same file.
- Maintain a clean, recoverable git state before executing high-risk refactors.
</layer_4_permissions>

<layer_5_verification>
Every step must self-verify using real signals: unit/integration tests, binary builds, coverage reports, and actual CLI outputs. Trust comes exclusively from observed execution results.
Record verification results in `checks.md` (or the final verification table) with one row per requirement:
`step | requirement | verdict | evidence`
Use `pass`, `fail`, or `unresolved`. Keep any missing evidence explicitly visible.
</layer_5_verification>

<layer_6_feedback>
Maintain two feedback loops:
- Error Recovery: when a step fails verification, re-run only that step with the failure reason, exact `stderr`/test output, and a "fix this step only" boundary. Cap retries at 3 attempts.
- Memory Loop: whenever a bug, subtle edge case, or user correction occurs, append an invariant rule to `<learned_rules>` in `AGENTS.md` so future sessions never repeat the mistake.
</layer_6_feedback>

<layer_7_completion>
Before finishing, evaluate the completion checklist against `{{CHECKS}}`. Every item must have observable proof:
- All target outputs exist and compile cleanly.
- Every check passes against the latest source tree and rebuilt `./mintrun` binary.
- All errors are resolved or explicitly documented.
- `AGENTS.md` includes any new rules learned during the run.
If the run limit is reached or blocked, return partial status with exact verdicts showing what passed.
</layer_7_completion>

<execution_loop>
1. Read `plan.md` and select the next ready step(s).
2. Execute independent steps in parallel.
3. Verify every output against its check (`go vet`, `go test`, `./mintrun`).
4. Retry only failed steps (up to `{{LIMIT}}`); never discard an entire batch for an isolated failure.
5. Merge accepted outputs and re-run the full repository check suite.
6. Continue until complete, blocked, or `{{LIMIT}}` is reached. Never loop infinitely.
</execution_loop>

<handoff>
After each phase in a multi-phase task, update `progress.md`:
- Plan: completed, active, and blocked steps.
- Outputs: exact relative paths to created or modified files.
- Decisions: what changed in the codebase or harness and why.
- Open issues: errors, uncertainties, and external blockers.
- Next step: the next immediately actionable step.
When resuming a session, read `AGENTS.md`, `plan.md`, and `progress.md` first, then continue from the recorded checkpoint.
</handoff>

<delivery>
Return `{{OUTPUT}}`, `plan.md`, `checks.md`, `progress.md` (when applicable), and the `AGENTS.md` diff.
State clearly what was verified, what passed, and what remains unresolved.
Report test coverage and usage metrics strictly from real command execution—never estimate or infer numbers from the prompt.
</delivery>
</prompt>
```

## `<learned_rules>` — Project Invariants

1. **Zero External Dependencies:** `go.mod` must only declare the module path and Go toolchain version (`go 1.24.0`). All cryptographic and network protocols (RS256 JWT, AWS SigV4, AES-256-GCM, SHA-256 pinning, MCP JSON-RPC 2.0) must be implemented using 100% Go standard library packages.
2. **No GitHub Actions CI (`.github/workflows`):** This repository does not use GitHub Actions. Never create or re-introduce a `.github/` directory.
3. **Zero-Secret & Zero-PII Leak Invariant:**
   - Every credential handled at runtime (Master Secret, `Lease.Env`, `Lease.Redact`) must pass through `core.Scrub()` (covering Raw, Base64, RawBase64, Hex, and URL-encoded forms) before reaching `stdout`, `stderr`, or `~/.mintrun/audit.jsonl`.
   - Never commit local absolute filesystem paths (such as user home directories or workspace paths), hostnames, device identifiers, or real tokens in source code, tests, comments, or documentation (`README.md`, `AGENTS.md`). Always use relative paths and `-trimpath` when building binaries.
4. **Approval Text Quotes Every Agent Field; the Dialog Literal Holds Only Escapes AppleScript Reads:** Every approver shows `core.ApprovalText`. Its first two lines under the header are `Sandbox: on` or `Sandbox: off` and `Network: blocked` or `Network: open`, written by mintrun and unquoted, ahead of every agent field, so no long request pushes them behind the TRUNCATED warning; they show the sandbox and network flags of the verdict that asks, never only the request's flags (rules 43, 46). When `req.Device` is set by the relay server (rule 47), `Device: <strconv.Quote(req.Device)>` follows right under `Network:`. `Hints:` comes next, under `Device:` when it is set and under `Network:` otherwise, also written by mintrun, unquoted, and ahead of every agent field: `Hints: none`, or the labels `approvalHints` finds, joined by commas in the fixed order of its one closed vocabulary, `approvalHintRules` (`delete`, `force`, `network-tool`, `encode`, `shell`, `external-url`). It reads only argv and the provider, never the purpose, params, or working directory, and matches each argument whole after ASCII lowercasing, so a `-X DELETE` or `--method delete` pair is `delete` through its `delete` word, while `/bin/rm` and `--method=DELETE` get no label. A bare `-f` is never `force`, because `gh api -f` sets a field. `external-url` is an `http://` or `https://` URL, up to the next space, whose `net/url` host is neither a domain in the provider type's `approvalOwnHosts` entry (an account shares its type's, rule 56) nor a subdomain of one; a URL that does not parse is external, and so is every URL of a provider type with no entry. The lowercasing is ASCII only because `strings.ToLower` folds U+0130 into `i`, so a host spelled with it would pass for `github.com`. The hints are advice: no decision, audit field, `PolicyDecision`, or `app.sock` key carries them. `TestApprovalHints` pins every word in both cases, the negatives, both pairs, the order, and the own and other hosts, with risky words planted in every other field; `TestOSApproval` pins five dialog literals (no match, all six labels in order, the `-X DELETE` pair, the provider's own URL and another host's) and a long request whose `Hints: delete` names an `rm` the cut hides; and 24 mutants on a copy (among them the line after `Command:`, quoted, dropped when empty, or above `Device:`, the labels sorted, `rm` matched as a substring, the provider's own URL called external, and a bare `-f` flagged) each fail one of them. It `strconv.Quote`s the provider, the vault, the scope, each permission, each param (sorted `"key"="value"`), each argv element, and the working directory, adds quoted `Purpose:` and `Client:` lines after `Working directory:` when they are set (last, so a long request is cut through these agent claims before any fact), and cuts the text on a UTF-8 boundary with a TRUNCATED warning (1,000 bytes in the dialog, 3,500 in Telegram, and in Slack short enough that the escaped text fits in 3,500; rule 34). A newline, quote, or bidi control (U+202E) in an agent field therefore shows as an escape and cannot fake a `Command:` or `Working directory:` line, push the command out of view, or reverse the text. An empty vault or working directory shows as `(not set: the default vault)` or `(not set: mintrun's own)`, unquoted, so no agent value can pass for it; neither is resolved, so the text never looks up the default vault or `mintrun`'s own directory. The working directory comes after the command, so a long command pushes it behind the TRUNCATED warning. `OSApproval` passes the text to `display dialog` through `%q`, which then writes only `\n`, `\"`, and `\\`. AppleScript reads those, `\t`, and `\r`, and rejects any other escape (error -2741, no dialog), which an unquoted ESC (`\x1b`) or U+202E (`\u202e`) would put in the literal. `TestOSApproval` decodes the literal the stub `osascript` logs and compares it with the exact text for an argument holding a fake `Command:` line, blank lines, and U+202E, and a working directory holding a fake `Working directory:` line and U+202E. It also pins the text of a request that sets neither vault nor working directory, which reads `Sandbox: off` where the first reads `Sandbox: on` (as both long cuts do), and the rest of the script, Deny as the default button included (rule 31). It checks that no other escape is left and cuts a long request twice, with and without a 1-byte pad: whether a byte cap lands inside a multi-byte rune depends on every byte before it, and once the `Vault:` line moved a single long request's cut onto a rune boundary, the test no longer caught a missing UTF-8 trim. 20 mutants (the old unquoted dialog; argv, provider, params, vault, or working directory unquoted; the vault or the working directory left out; the not-set notes dropped; no cap; no UTF-8 trim; `%+q` in the dialog; `Allow` as the default button; the sandbox line moved after `Command:` or to the end, always `on`, always `off`, its values swapped, quoted, or dropped) each fail it. Write bidi and control characters in source as escapes, never raw, and scan changed files for U+202A–U+202E and U+2066–U+2069 with a planted positive control (rule 22): an edit tool, and a command typed through one, can turn a typed `\u202e` into the character itself. A scanner therefore builds its planted control with `chr(0x202E)`, which keeps its own source clean enough to scan too. The edit tool also turned a typed `\u00e9` into the character itself. A file that held no non-ASCII byte before an edit is scanned for any after it. Repair it through a script that builds the backslash with `chr(0x5c)`, never by retyping the escape in the edit tool. An edit tool can also drop a trailing space from its replacement: while the macOS app hooks were brought up to date with `main`, `"\nPurpose: "` lost its space and `TestPurposeValidation` failed, so end an edit's old and new text on a non-space character.
5. **Verified Statement Coverage (`> 90%`):** Never report estimated coverage numbers. Always execute `go test -count=1 -coverprofile=coverage.out ./... && go tool cover -func=coverage.out` and remove temporary `coverage.out` artifacts before committing. To measure a tag, export it (`git archive <tag> | tar -xf - -C <dir>`) and run both commands inside the export: `-func` maps each profile block onto the functions of the source in the current checkout, so a tag's profile read in a later checkout totals differently (`v0.6.0` reads `92.6%` in its own tree and `92.7%` in a later one).
6. **Keep `./mintrun` Binary Synchronized:** After modifying any file under `cmd/` or `internal/`, rebuild with `go build -trimpath -o mintrun ./cmd/mintrun` so local CLI and MCP server executions run the latest code.
7. **Lease IDs Are Public Handles, Never Secrets:** `Lease.ID` is returned to agents (`ExecResult.LeaseID`, MCP) and written to `audit.jsonl`, so providers must set it to an opaque non-secret handle (e.g. `gh-inst-<installation_id>-<unix>`). A credential needed only by `Revoke` goes in `Lease.RevokeSecret` (`json:"-"`, never serialized); the runner still scrubs `lease.ID` against all known secrets as defense in depth.
8. **Scrub Every `ExecBlind` Exit Path, Not Just Successful Output:** Errors (especially `provider.Mint` failures, which can echo plugin stderr or API response bodies), `LeaseID`, and the audit `command`/`error` fields must all pass through `Scrub()` with the master secret plus every lease secret. Return scrubbed error text with `%s`, never wrap a raw error that may contain a secret with `%w`. Every `ExecBlind` exit writes exactly one audit entry with an `outcome`, the unknown-vault, unknown-provider, and unloadable-master exits included (`failed`, exit 1); the sole two-entry exception is `Runtime.MintLease` on the team relay server, which writes one `outcome: "minted"` entry when a lease is handed to a device and a second entry (`done`/`failed`/`stopped`/`interrupted`/`timed_out` on `POST /v1/revoke`, or `unreported` when the lease's expiry timer fires first; rule 47). Every entry written after the master is loaded scrubs `client` and `purpose` like `command`. `ExecRequest.Task`, `Client`, `Via`, and `Device` are `json:"-"`, so an agent's MCP arguments or a relay client's JSON body cannot set them, and `Task` is a `rand.Text()` public handle (rule 7). An exit's error names no path under the home either, because it reaches agents and `audit.jsonl` (rule 36): `readMap` fails with `read vault.json: <cause>` and `ExternalPlugin.call` with `plugin "<name>" failed: <cause> (<stderr>)`, the `*fs.PathError` cause only, and since every file-vault read and plugin call goes through them, `mintrun exec`, `secret check`, and `doctor` show no path either. `ExecBlind` still wraps the vault error with `%w` for rule 37's `errors.Is`. `call` passes what a plugin writes itself, its `stderr` (a crashing Python script's traceback names the script's path) and its reply's `error` field, through `quote`. `quote` scrubs the master first, because the runner scrubs only the whole master and a home replaced inside it would leak the rest, then shows the user's home as `~` and the mintrun home as `$MINTRUN_HOME`; `~` is matched first, so the default home reads as `~/.mintrun`. A relative or root `HOME` is left alone: a root one would win over the mintrun home and spell it out with `~` for every `/`. Only a home written as given is replaced, so a path with its symlinks resolved or an escaped path still gets through: this keeps a crash from naming the home, not a plugin set on leaking it. A failed file-vault write still names the file (only the CLI writes the vault). `TestMCPBridgeExecUnreadable` pins a `vault.json` that is a directory and one without read permission (skipped as root, which reads it anyway), and a plugin provider and a plugin vault whose entrypoint cannot start, through the `mintrun_exec` reply and the audit entry, and 6 mutants on a copy each fail it. `TestMCPBridgeExecPluginHomes` pins five cases through the exact `mintrun_exec` reply and audit `error`, and checks that neither holds either home or the secret: a plugin provider whose `stderr` names its own path, a file under the user's home, and the master, which holds a home path too; a plugin vault whose `stderr` names the first two; a plugin provider whose `error` field names both homes; and a relative and a root `HOME`. 13 mutants on a copy each fail it, a scrub after the replacement among them.
9. **File Vault Requires a Passphrase, Derived With a Salted KDF:** The AES-256-GCM fallback vault (`internal/builtin/keychain.go`, the at-rest store on non-macOS hosts) must never derive its key from the filesystem path or any other guessable value. Require a non-empty `MINTRUN_VAULT_KEY` and derive the key with `crypto/pbkdf2.Key(sha256.New, pass, salt, …)` using a per-vault random salt persisted in `vault.json` (`__salt__`). `readMap` must reject any file lacking both `__aes256gcm__` and `__salt__` (legacy plaintext and foreign formats are fail-closed, not silently trusted). This is a breaking on-disk format: an existing `vault.json` must be removed and re-created with `mintrun secret set`. Write the vault atomically (temp file + `Sync` + `os.Rename`) and always check `crypto/rand.Read` errors for both salt and nonce.
10. **Plugins Cannot Shadow Built-ins, Escape Their Directory, or Install Unverified:** `Registry.Register` must reject a non-builtin plugin whose name matches an existing built-in vault/provider/bridge. Any plugin name used as a path segment must pass `safePluginName` (single segment, no `.`/`..`/separators) on both install and remove. Remote install must require an out-of-band `#sha256=<hex>` digest (a bundle's self-declared digest is attacker-controlled and proves nothing) and an `https://` URL, with a loopback-only carve-out for plaintext (still integrity-checked by the mandatory digest); a remote bundle is always forced `Builtin: false`.
11. **Child Env Never Carries the Vault Passphrase or Relay Token; Clean Mode Only Tightens:** `ExecBlind` builds the child environment with `childEnv`. `MINTRUN_VAULT_KEY` and `MINTRUN_RELAY_TOKEN` are never inherited, even when `allowed_env` matches them (`["*"]` included). Clean mode (`ExecRequest.CleanEnv` **or** policy `clean_env` **or** a non-empty `allowed_env`) keeps only `PATH`, `HOME`, `TMPDIR`, `USER`, `LANG`, `TERM`, `SSL_CERT_FILE`, the `allowed_env` globs, and `Lease.Env`. A request (CLI `-clean-env`, MCP `clean_env`) may tighten policy but never loosen it.
12. **Providers Scrub Their Own Derived Secrets; Static Mode Is Explicit and Key-Free:** The runner knows the master secret only as one whole string, so a provider that derives sub-secrets (a signed JWT assertion, a parsed private key from a JSON master) must scrub them from its own error text (e.g. `GCPProvider.postForm`) and list them in `Lease.Redact`. Static mode must be requested explicitly (`static` permission or `mode=static`) so the `allow_static` policy gate applies, and must refuse long-lived key material (GCP refuses a service-account JSON or PEM).
13. **GCP Revocation Is Best-Effort; Revocation Tokens Go in the Body:** Google does not revoke service-account access tokens server-side and fixes their lifetime (≤1h), so `revoked=false` is expected and neither `-ttl` nor `max_ttl_seconds` can shorten a GCP lease; never document otherwise. Send revocation tokens in the POST body, never in a URL query.
14. **Secrets Reach Helper CLIs on stdin, From Absolutely Resolved Binaries:** Pass secrets to helper CLIs (e.g. `secret-tool store`) on stdin, never argv (visible in `ps`). Use an `exec.LookPath` result only when `err == nil`, because Go returns a relative-path match together with `exec.ErrDot`. `mintrun secret set` reads piped stdin whole, so multi-line secrets (service-account JSON, PEM) are never truncated to their first line, and a failed stdin read is fatal so a partial read never overwrites a stored secret.
15. **Run Each Step's Verification Check Verbatim and Confirm It Selects the New Tests:** A `go test -run` regex in `plan.md` that matches no test still exits `ok`, so a renamed or differently named test silently drops out of the check (for example, `TestKeychainLinux` does not match `TestKeychainVaultLinuxSecretTool`). Run each step check with `-v` and confirm every new test appears as `--- PASS`; fix the regex or the test name when it does not. Go splits a `-run` pattern at each `|` outside brackets and parentheses before it splits each alternative at `/`, so `-run 'TestA/sub|TestB'` runs `TestA`'s `sub` subtests and every test `TestB` matches; read the `-v` output before calling such a pattern broken.
16. **MCP Governance Tools Are Read-Only Views of the Real Gate:** `mintrun_policy_check` must call `core.(*Runtime).CheckPolicy`, the same function `ExecBlind` enforces through `checkPolicy`, and must never open a vault, mint, exec, call `ApprovalFunc`, or write `audit.jsonl`. Add every new gate rule to `CheckPolicy`, never to `ExecBlind` alone (`TestCheckPolicyMatchesExecBlind` pins each denial reason to the `ExecBlind` error). Request validation (empty `provider`/`command`) lives there too, so those failures are audited with exit 126 like any denial. So does the vault rule: the vault is the operator's choice (`MINTRUN_VAULT`, or the CLI's `-vault`), so after decoding a `mintrun_exec` or `mintrun_policy_check` request the bridge sets `ExecRequest.FromAgent` (`json:"-"`, so no argument sets or clears it), and `CheckPolicy` denies an agent's request that names any vault, even the default one. The CLI never sets the flag. `TestCheckPolicyMatchesExecBlind` pins the denial and the CLI's `-vault`, `TestMCPBridgeRefusesVault` pins the exact reason through both tools and the exit-126 audit entry, and 11 mutants on a copy each fail one of them. So does the timeout rule: neither `mintrun exec` nor `mintrun mcp` takes a time limit, so an agent's command is killed after 5 minutes like the CLI's, and `CheckPolicy` denies an agent's request that sets `timeout_seconds` to anything but 0 (a negative value too, which `ExecBlind` would read as the default: an agent sets none). `TestMCPBridgeRefusesTimeout` pins the exact reason through both tools and the exit-126 audit entry, and `TestCheckPolicyMatchesExecBlind` pins both agent refusals for a provider `policy.json` has no rule for, so neither moves under a provider's rule. The tools' input schema lists every argument `ExecRequest` decodes except the refused `vault` and `timeout_seconds`, `approve` included (it only adds a human check): `TestMCPExecSchema` walks the struct and its embedded `MintRequest`, so a new field fails it until it is listed or refused, and 17 mutants on a copy each fail one of these tests. Both refusals are request validation: they report `blocked_by: invalid_request` and run before the pause, which `TestCheckPolicyMatchesExecBlind` pins on a paused runtime. So is an agent's empty or blank permission list (rule 58), and the schema marks `permissions` required beside `provider` and `command`. `mintrun_audit` shows agents each entry's verdict, never text an agent wrote: `scope`, `permissions` and `purpose` are blank, a non-empty `error` is `[MINTRUN:REDACTED]` (`outcome`, `blocked_by` and `exit_code` keep the verdict), the command is `argv[0]`'s base name plus `[MINTRUN:REDACTED]`, and the provider and that base name pass through `shortLabel` (only `[A-Za-z0-9._ ()@-]`, cut to 64 bytes). Every entry is shown that way, not only a blocked one. An entry written before the master loads keeps the request raw, and `Scrub` removes only secrets the runner holds. A `*` pattern, a glob such as `*.example.com`, an empty list, or no rule for the provider lets free text through as a scope or permission. The errors quote the scope, a permission, the provider, `argv[0]`, the installation ID and the vault name. `client`, `lease_id` (rule 7), `task`, `via`, and the numbers, booleans (`sandbox` among them, rule 43) and timestamps are shown. The on-disk log keeps every field for the operator. `TestMCPBridgeGovernanceTools` plants canaries in a blocked exec and in a failed one; each is in `audit.jsonl` and in no `mintrun_audit` reply, and 11 mutants each fail it. An `audit.jsonl` that exists but cannot be read (a directory, no read permission, an I/O error) fails `mintrun_audit` with `read audit log: <cause>`, the `*fs.PathError` cause only, never the path, which names the home (rule 36); `mintrun audit` prints the path to the operator on `stderr`. `TestMCPBridgeAuditUnreadable` pins a directory and a `chmod 000` file (skipped as root, which reads it anyway), and 4 mutants on a copy each fail it. Pause, the purpose check, and the read of `policy.json` run in `decide` (the body of `CheckPolicy`), in that order, right after request validation. Only a not-exist `Lstat` means no rules; any other failure denies (`policy_file`, with no path in the reason), and a home whose pause file cannot be checked is denied as `paused` first. After an approval allows, the gate runs again, so a pause or a rule saved while the request waited still applies, and `ExecBlind` hands `childEnv` the `allowed_env` of the rule it checked last, which `decide` returns beside the decision so `PolicyDecision` stays comparable. One vault read is the exception: the optional semantic screen (rule 53) reads the default vault's `jev` key on first use, never `req.Vault`, because `mintrun_policy_check` runs the same screen `ExecBlind` runs; `CheckPolicy` still mints nothing, execs nothing, calls no `ApprovalFunc`, and writes no `audit.jsonl`.
17. **Format Only This Checkout:** `.claude/worktrees/` can hold other sessions' git worktrees, and `gofmt` walks into dot-directories (unlike `go vet ./...`, which skips them), so `gofmt -s -w .` can rewrite another session's files. Run `gofmt -s -l .` first; if it lists anything under `.claude/`, format the repo's own packages only (`gofmt -s -w cmd internal examples`). The same goes for `grep -r .` scans: scope repo scans to `cmd internal examples` so they never match stale copies under `.claude/worktrees/`.
18. **Keychain Secrets Travel on `security -i` stdin, Long Ones in Checksummed Parts, and Keystore Fallbacks Are Loud:** `security add-generic-password -w <secret>` puts the secret on argv, so `keychainWrite` sends one `add-generic-password -U … -X <hex>` line to `/usr/bin/security -i` on stdin. `security -i` splits a line longer than 4095 bytes (newline included) and stores a corrupted item, so such a line is never sent. Hex doubles the size and the service name shares the line, so one item holds about 2 KB of secret, less for a longer key: a test that expects parts must size its value against its own key (a 2,001-byte value still fit in one line for the integration test's key). `keychainSet` stores a longer secret, or one starting with the header prefix that could pass for a header, as at most 16 parts of 1,500 bytes under a fresh `rand.Text()` generation. It writes the key's header item (`mintrun-chunks:v1:<gen>:<n>:<sha256 hex>`) last and only then removes the previous generation's parts, so a reader assembles the old secret or the new one, never a mix; a failed part write removes the new parts and leaves the old secret in place. `keychainGet` checks the SHA-256, and a missing or altered part is an error, never a quiet miss. A secret over 24,000 bytes goes to the file vault with a warning. Read with `find-generic-password -g` and parse its stderr, never `-w`, which hex-dumps any value holding a newline or a non-ASCII byte. Exit 44 (`errSecItemNotFound`) is a quiet miss; any other keystore failure prints `warnFallback`'s warning before the file vault takes over. No warning or error may quote the secret or the helper's stderr, which can hold it.
19. **A Capped Stream Never Ends Inside a Secret:** `cappedBuffer` keeps the first `MaxOutputBytes` (4 MiB) of each child stream and never fails a `Write`, since an `EPIPE` would kill a chatty child. `Scrub` matches whole secrets only, so a cut stream first loses any tail that is a proper prefix of a secret variant, and the trim repeats until no tail is one; then it is scrubbed, `[MINTRUN:TRUNCATED n bytes]` is appended, and `truncated` is set. A single pass leaks: a secret that starts and ends with the same byte and ends exactly at the cap loses only its last byte (`TestExecBlindOutputCap` pins this case).
20. **The Blind Child Runs in Its Own Process Group, So `main` Must Catch Every Stop Signal:** On Unix, `killProcessGroup` sets `Setpgid` and a `cmd.Cancel` that SIGKILLs `-pgid`, but only while the child is unreaped (`Signal(0)` returning `os.ErrProcessDone` means its pid may already be reused). `cmd.WaitDelay` (`PipeWaitDelay`, 5 s) bounds the wait for pipes a leftover process still holds; `exec.ErrWaitDelay` after a clean exit counts as exit 0 and is still revoked and audited. The child's group is not the terminal's foreground group, so Ctrl-C and a hangup reach only `mintrun`: `main` must keep `os.Interrupt`, `SIGTERM`, and `SIGHUP` in `signal.NotifyContext`. Without `SIGHUP`, a hangup killed `mintrun` (exit 129) before it revoked, the child kept running, and nothing was audited. A child that reads `/dev/tty` gets `SIGTTIN`. A `Track` stop cancels the run with `errStopped` and kills the group the same way. A stop already in when `Track` returns is caught by a check made then; that check only narrows a race, so its test runs under `runtime.GOMAXPROCS(1)`, where the watcher ran after `Start` in 20 of 20 runs. On macOS 27.0 a group kill misses a process the child is still creating (396 of 2000 kills during a fork), so `Cancel` first stops the child with `Process.Signal(SIGSTOP)`, waits `forkSettle` (10 ms) for the fork to finish, and only then runs the guarded group kill. A stopped child cannot exit, so it stays unreaped until the kill. Only the child is stopped, never the group: a member stopped after the child's exit stays stopped forever once the guard finds the child reaped. A fork by another member of the group, or one slower than `forkSettle`, can still survive. `TestKillProcessGroupFork` pins the fork; `TestKillProcessGroupAfterReap` and `TestKillProcessGroupReapedDuringSettle` pin the guard; a fix must never signal a reused process group.
